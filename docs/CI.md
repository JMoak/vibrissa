# Vibrissa in CI

`vib run` is the gate. It exits `0` when every case passed, the manifest lock matches, and
(with `--check`) no check failed; `1` otherwise; `2` for usage, config, or connection
errors. The rest of this page is about getting good artifacts out of that run.

Related: [CLI.md](./CLI.md#vib-run), [CONFIG.md](./CONFIG.md#reporters).

## A `ci` profile

Keep CI settings in config so local and CI runs differ only by `--profile ci`. `vib init`
writes this one:

```json
{
  "servers": { "default": { "cmd": "node", "args": ["dist/index.js"] } },
  "globs": ["tests/integration/**/*.json"],
  "profiles": {
    "ci": { "reporters": ["console", "github", "junit", "json"], "check": true, "requireManifest": true }
  }
}
```

| Key | Why |
|---|---|
| `reporters` | Console log, GitHub annotations and job summary, `reports/junit.xml`, and `reports/results.json` (the [baseline](#delta-gating) input). |
| `check` | Spec sanity and description lint gate the run. |
| `requireManifest` | A missing lock fails the run instead of warning, so an unrecorded surface cannot pass. |

`vib init` also adds `reports/` to `.gitignore`.

The `github` reporter emits annotations only when `GITHUB_ACTIONS=true`, so the same
profile stays quiet on a laptop; there it writes its summary to `reports/summary.md`.

## GitHub Actions

`vib init --ci` writes `.github/workflows/vibrissa.yml` (for a Node project):

```yaml
# Vibrissa contract tests: cases + manifest lock + spec/description checks.
# Generated by `vib init --ci`. Uses the "ci" profile in vibrissa.json; reports/ is uploaded on failure.
name: vibrissa

on:
  push:
    branches: [main]
  pull_request:

jobs:
  contract:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run build --if-present
      - run: npx vib run --profile ci
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: vibrissa-reports
          path: reports/
```

| Step | Why |
|---|---|
| `npm run build --if-present` | Cases test the built server, the artifact your users run. |
| `vib run --profile ci` | The gate. The profile carries the flags: reporters, checks, `requireManifest`. |
| `upload-artifact` with `if: failure()` | Keeps `junit.xml`, `results.json`, and traces from failing runs, which are the runs you need them from. Use `if: always()` to keep green runs too (for [baselines](#delta-gating)). |

For Python projects the workflow adds `setup-python` and `pip install -e .`; for Go,
`setup-go`. Projects without a `package.json` run Vibrissa with
`npx --yes --package @jmoak/vibrissa vib`.

`vib init --ci` in a project that already has `vibrissa.json` writes only the workflow (and
reports whether the `ci` profile is present). Common edits: add
`permissions: { contents: read }` and SHA-pinned actions if your org requires them.

The `github` reporter produces:

- `::error` annotations on the case file for each failed case, failed check, and manifest
  drift; `::warning` for warnings, warned checks, and budget breaches on passing cases.
- A markdown job summary in `$GITHUB_STEP_SUMMARY`: totals, failures with diffs, checks,
  manifest drift, and a collapsed table of every case.

## GitLab and Jenkins (JUnit)

The `junit` reporter writes `reports/junit.xml`: one `<testsuite>` per server, plus
`vibrissa:manifest` and `vibrissa:checks` suites when those ran. Assertion failures are
`<failure>`; errors, timeouts, and load problems are `<error>`; skipped cases are
`<skipped>`.

GitLab:

```yaml
mcp-contract:
  image: node:22
  script:
    - npm ci
    - npm run build --if-present
    - npx vib run --check --reporter console,junit,json
  artifacts:
    when: always
    paths: [reports/]
    reports:
      junit: reports/junit.xml
```

Jenkins (declarative):

```groovy
pipeline {
  agent { docker { image 'node:22' } }
  stages {
    stage('mcp-contract') {
      steps {
        sh 'npm ci && npm run build --if-present'
        sh 'npx vib run --check --reporter console,junit,json'
      }
    }
  }
  post {
    always {
      junit 'reports/junit.xml'
      archiveArtifacts artifacts: 'reports/**', allowEmptyArchive: true
    }
  }
}
```

Anything that reads JUnit works the same way. For TAP consumers use `--reporter tap`
alone: it writes to stdout, as `console` does.

## Inside a Vitest suite

Teams that already gate on Vitest can run the contract suite as Vitest tests and get one
report. Vitest is an optional peer dependency.

```ts
// tests/mcp.contract.test.ts
import { describeCases } from '@jmoak/vibrissa/vitest'

await describeCases({ profile: 'ci', checks: true, title: 'mcp contract' })
```

One `describe` block holds, in order:

- `manifest lock (<path>)` for each server with a lock (a failing test when the lock is
  missing and `requireManifest` is on), failing on drift with the rendered diff;
- `checks (<server>)` when `checks` is set (or config `check: true`), failing on failed
  checks;
- one `it` per case (`it.skip` for `skip`), failing with the reason and mismatches.

`DescribeCasesOptions` (all optional): `globs` (default: config globs), `config` (a path,
or `false` to pass `servers` and `globs` yourself), `profile`, `cwd`, `title` (default
`"vibrissa"`), `checks` (`true`, or `{ allow, severity }`), `lockManifest` (default `true`),
`api` (`{ describe, it, beforeAll, afterAll }`; default Vitest globals, else a lazy
`import('vitest')`, hence the `await`), and the runner options (`timeoutMs`, `normalize`, ...).
There is one server session per server for the whole block.

## Sharding across jobs

`--shard i/n` runs every n-th case of the id-sorted suite, starting at case i. Every case
lands in exactly one shard; a flow is one case, so it is never split.

```yaml
jobs:
  contract:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        shard: [1, 2, 3, 4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci && npm run build --if-present
      - run: npx vib run --profile ci --shard ${{ matrix.shard }}/4
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: vibrissa-reports-${{ matrix.shard }}
          path: reports/
```

Give each shard's artifact a distinct name. Each shard verifies the manifest lock too, so
drift fails every shard. Inside one job, `--concurrency N` runs N workers, each with its
own server session.

## Delta gating

Absolute gates block every PR while one case is known broken. With `--baseline`, only
**regressions** against a previous run fail:

```bash
vib run --reporter console,json --baseline reports/last-green.json
```

| Case now | In the baseline | Result |
|---|---|---|
| fails | passed, or absent | **regression**: fails the run |
| fails | failed | reported as "still failing", not gated |
| passes | passed | **regression** if it got more than 50% slower and at least 10 ms slower |
| passes | failed, or absent | fine |

Skipped cases are ignored on both sides. The verdict shows up as a `baseline/regressions`
check in every reporter. Manifest drift and failed checks still fail the run: the baseline
only relaxes case results.

The baseline is any `results.json` written by the `json` reporter (if it is missing or
unreadable, the run warns and gates on absolute results). Cases are compared by `caseId`,
the case file path relative to the config directory, so files from different machines
compare cleanly. The shape, abridged:

```json
{
  "version": 1,
  "generator": "vibrissa",
  "ok": true,
  "complete": true,
  "startedAt": "2026-10-28T12:00:00.000Z",
  "finishedAt": "2026-10-28T12:00:00.840Z",
  "servers": [{ "name": "default", "era": "modern", "protocolVersion": "2026-07-28" }],
  "summary": { "total": 12, "passed": 12, "failed": 0, "skipped": 0, "updated": 0, "durationMs": 840, "checks": { "passed": 0, "failed": 0, "warned": 0 }, "manifestDrift": 0, "warnings": 0 },
  "cases": [
    { "id": "tests/integration/echo.basic.json", "caseId": "tests/integration/echo.basic.json", "name": "echo basic", "file": "tests/integration/echo.basic.json", "server": "default", "line": 1, "status": "passed", "durationMs": 4 }
  ],
  "manifests": [{ "path": "tests/integration/__manifest__.json", "server": "default", "status": "ok" }]
}
```

Empty arrays (`checks`, `warnings`, `tags`, `flaky`) are omitted. A repeated or sharded run
adds top-level `repeat` and `shard: { index, total }`, plus `summary.runs` (executions) and
`summary.passRates`. Failed cases also carry `errorKind`, `reason`, `mismatches`,
`expected`, `actual`, `steps`, `budget`, `updateSkipped`, `tracePath`, and `stderrPath`.
Each mismatch is patchable: `{ path, message, expected, actual, field, pointer, stepIndex? }`,
where `field` is the case key (`expect`, `expectError`, `expectInputRequired`,
`expectTask`, or `structuredContent` for an `outputSchema` violation), `pointer` is an
RFC 6901 pointer into the case file (`/steps/1/expect/content/0/text`), and `stepIndex` is
the flow step. The full type is `JsonReport`, exported from the package.

Producing the baseline on `main` and using it in PRs with GitHub Actions:

```yaml
# push to main, after a green run
- run: npx vib run --profile ci
- run: cp reports/results.json reports/last-green.json
- uses: actions/upload-artifact@v4
  with:
    name: vibrissa-last-green
    path: reports/last-green.json

# pull_request
- uses: dawidd6/action-download-artifact@v6
  with:
    workflow: vibrissa.yml
    branch: main
    name: vibrissa-last-green
    path: reports/
  continue-on-error: true
- run: npx vib run --profile ci --baseline reports/last-green.json
```

`actions/download-artifact` reads only the current run's artifacts, hence the third-party
action for "the last `main` run". Committing `last-green.json` to the repo also works and
needs no action.

## Repeat and flaky policy

`--repeat N` runs every case N times and reports a pass rate per case:

- A normal case must pass all N runs.
- A case marked `"flaky": true` passes when its pass rate is at least 0.5.
- `results.json` lists `summary.passRates` and `summary.flaky` (cases with a pass rate
  strictly between 0 and 1), marked or not.

A nightly job with `--repeat 10` finds flakes before they block PRs. Fix them, or mark them
and track them; do not add retries to the PR gate.

## Traces on failure

Every failing case gets a JSON-RPC transcript, and the server's stderr when there was any:

```
reports/traces/<case path without .json>.ndjson       one entry per line: { "dir": "out" | "in", "ts", "message" }
reports/traces/<case path without .json>.stderr.txt   the server's stderr during the case
```

With `--repeat`, files get a `.run<N>` suffix. `--trace` (or `trace: true`) writes them for
passing cases too. Their paths appear in the console failure output, in `results.json`
(`tracePath`, `stderrPath`), and in JUnit. Upload `reports/` with `if: always()` and the
transcript of a CI-only failure is one click away. (A `vib show-trace` pretty-printer is
[planned](./CLI.md#planned); until then the files are plain NDJSON.)

## Manifest and checks in CI

- Commit the manifest lock. A run whose live surface differs fails with a per-field diff
  that marks breaking changes (annotated on GitHub). A missing lock is a warning, or a
  failure with `requireManifest: true` (the scaffolded `ci` profile sets it).
- One lock serves every protocol era (`protocolVersion` and `listMeta` are ignored by
  default), so a `legacy` profile job checks the same file.
- Never pass `--update`, `--update=all`, or `--update-manifest` in CI. Accepting a change
  is a review decision: run it locally and commit the diff with the PR that caused it.
- `--check` (or `check: true` in the profile) runs `vib check` as part of the gate.
  `failed` checks fail the run; `warned` ones are annotations only. Tune them with
  `checks.allow` and `checks.severity` ([CONFIG.md](./CONFIG.md#checks)).
